1. Архитектура процесса
Заявитель заводит сделку в Б24 → сотрудник ЦМК её согласует → из одного пакета данных 1С параллельно создаёт два связанных документа: Заказ клиента (ЗК) и Заказ поставщику (ЗП) → предоплата → производство → отгрузка → при наличии постоплата и закрывающие документы. Номенклатура может меняться на любом этапе — это отдельный сквозной процесс (Этап 9).
→  ЗК и ЗП всегда создаются парой из одного пакета, никогда по отдельности.  —  зачем: клиентские обязательства (ЗК) и производственная/закупочная потребность (ЗП) должны появляться и обновляться синхронно — иначе документы разойдутся.
→  ЗК и ЗП связаны двумя способами: общим «№ заказа Битрикс» (ID-CATEGORY_NAME) и явной ссылкой в ЗП «[ДП] Номер заказа по данным поставщика» = номер ЗК.  —  зачем: первое — для сверки на стороне Б24, второе — чтобы 1С могла построить связь документов внутри себя, не обращаясь к Б24.
→  Товарные позиции (PRODUCT_ROWS) в ЗК и ЗП идентичны; контрагенты и служебные поля (склад, направление, статус) — разные.

2. Этап 1 — Новая сделка
Триггер: заявитель создаёт сделку в воронке ЦМК.
→  Не давать сделке двигаться дальше без заполненных полей: Заказ Клиента, Подразделение, Группа проектов, Наша компания, Руководитель, Утверждающий, Требуемая дата производства.  —  зачем: без этих полей документы в 1С будут созданы с неполными данными, и часть последующих правил (например подбор ЗП по подразделению) не сможет отработать.
→  Требовать проектную документацию (Проект, АВП, ПП, ТЗ, Расчёт ценообразования, Разработка проекта КМД) только если Подразделение = «7П» или «71П».  —  зачем: по регламенту проект перед производством обязателен только для этих двух подразделений — для остальных это лишнее требование, которое просто остановит процесс.
→  Заполнять номенклатуру автоматически по шаблону через функцию «Комплектация набора», если заказ типовой.  —  зачем: убирает ручной ввод повторяющегося состава для стандартных заказов. Этот момент надо описать по подробнее 
→  Перед созданием сделки проверять дубли по номеру «Заказ клиента» в рамках воронки ЦМК.  —  зачем: чтобы под один и тот же заказ клиента не завести вторую сделку и, как следствие, вторую пару ЗК/ЗП в 1С.
Это первый, но не последний рубеж контроля дублей. Финальная проверка — в 1С, непосредственно перед созданием ЗК/ЗП (Этап 3.2), потому что только там можно поймать гонку между двумя параллельными отправками одного пакета.
3. Этап 2 — Согласование сотрудником ЦМК
Триггер: сделка создана, обязательные поля и документация (если требуется) на месте.
→  Сотрудник ЦМК проверяет проект.
→  Если нужной номенклатуры нет в справочнике — завести её через Google Doc / оператора ЦМК: присвоить артикул, создать спецификацию, определить цену.  —  зачем: 1С не может продать и произвести то, чего нет в справочнике номенклатуры.
→  После проверки — действие «Согласовать заявку», затем проверка «Сделка согласована заявителем?».
→  Кладовщик проверяет достаточность сырья.
→  При нехватке сырья — создать заявку в воронку «Снабжение» и перевести сделку на стадию «Ожидание прихода на склад» такой стадии у нас нету в воронке  с полной блокировкой дальнейшего движения.  —  зачем: производство физически не может начаться без сырья; блокировка не даёт сделке формально проехать дальше по воронке, пока сырья нет по факту.

4. Этап 3 — Формирование ЗК и ЗП в 1С:ERP
Триггер: сделка согласована на Этапе 2.
4.1 Создание документов
→  Одним пакетом отправлять данные в 1С; 1С параллельно создаёт ЗК и ЗП. Полный перечень полей — Приложение А.
→  Перед созданием документов повторно проверять дубль по «№ заказа Битрикс» (ID-CATEGORY_NAME) — уже на стороне 1С.  —  зачем: проверка в Б24 на Этапе 1 не защищает от повторной отправки одного и того же пакета; финальный барьер должен стоять там, где документ физически создаётся.
→  При обнаружении дубля — прервать создание документов и вернуть ошибку без частичного создания ЗК или ЗП.
Ответ 1С при дубле:
{
  "message": "...",
  "code": "DUPLICATE_ORDER"
}
→  Успешный ответ 1С должен содержать оба документа одним пакетом — client_order и supplier_order, каждый с DOC_NAME, GUID, DOC_NUMBER, DOC_YEAR.  —  зачем: Б24 должен получить номера обоих документов за один REST-вызов, чтобы не делать два отдельных запроса и не ловить рассинхрон между ЗК и ЗП.
Ответ 1С при успешном создании:
{
  "client_order": { "DOC_NAME": "...", "GUID": "...", "DOC_NUMBER": "...", "DOC_YEAR": "..." },
  "supplier_order": { "DOC_NAME": "...", "GUID": "...", "DOC_NUMBER": "...", "DOC_YEAR": "..." }
}
ОТвет 1С будет отправлен двумя разными пакетами 
4.2 Правила подбора значений
→  Если справочное значение не найдено — оставлять поле пустым; если найдено несколько совпадений — брать первое найденное.  —  зачем: пустое поле сотрудник сразу видит и может донастроить руками; молча выбранное неверное значение — опаснее, потому что расхождение обнаружат гораздо позже.
→  Поле «Договор» в ЗК заполнять только если ACTIVITY = «ЦМК Другие»; иначе оставлять пустым.
→  Банковский счёт поставщика в ЗП подбирать по БИН (поле COMPANY): для БИН 080840010555 и 201040028925 — по фиксированным GUID (Приложение А); для БИН 110440011140 GUID пока не определён.
 
1) если COMPANY=«080840010555», то «9570 в АО "Банк ЦентрКредит" (KZT)» 
                                                               - b79ec27d-da55-11ef-bb0c-00155d0a1043
2) если COMPANY=«201040028925», то «7266 в АО "ForteBank" (KZT)» 
                                                                - 0e0ced99-6b51-11ef-bb02-00155d0a1023
3) если COMPANY=«110440011140», то «KZ748560000004477830 в АО "Банк ЦентрКредит"» Давай напишем это вот так 
Открытый вопрос: нужен GUID банковского счёта для БИН 110440011140 — без него подбор для этого поставщика останется ручным. См. Приложение В, п. 4.
4.3 Отказоустойчивость
→  При транспортной ошибке — 3 повторные попытки с интервалом 5 минут.
→  Если все попытки исчерпаны — не продолжать сделку молча: записать в Timeline JSON-лог ошибки, заблокировать автоматический переход стадии и отправить уведомление в Telegram (Deal ID, Module, Error Type: Timeout/Logic/Connection/Duplicate, Body Snippet).  —  зачем: сделка не должна визуально доехать до следующей стадии, если ЗК/ЗП по факту не созданы — иначе все последующие этапы будут работать с несуществующими документами. Телеграмма не будет тут просто будет так чтобы они сообщили уведомлением отделу “Отдел по оптимизации бизнес-процессов 2”
→  После устранения причины технический специалист вручную перезапускает бизнес-процесс.
5. Этап 4 — Предоплата
Триггер: ЗК и ЗП созданы (Этап 3 завершён).
→  Проверять PREPAYMENT_PERCENTAGE: 0% — пропустить этап и сразу перейти к производству; > 0% — уведомить заявителя и запустить субпроцесс оплаты. Не битрикс же в субпроцессе оплаты Битрикс просто ждет пока поступят деньги 
5.1 Субпроцесс оплаты
Это тот же субпроцесс, что используется в Этапе 10 «Оплата поставщику» — описан один раз, не дублируется.
•  Потребность в оплате → указать ЗП и сумму → фин.отдел → заявка на расходование ДС на основании ЗП → списание безналичных ДС → банкинг. Это разработчикам вряд ли нужно так как они не учатсвуют в этом процессе тут в этом ТЗ мы говорим только о Б24 и 1С и все 
5.2 Фиксация оплаты
→  При проведении «Списание безналичных ДС» по ЗП 1С передаёт статус в Б24.
→  Сравнивать: SUPPLIER_ORDER_PAYMENT_SUM ≥ Сумма_предоплаты_из_Сделки. Тут нужно показать какой ответ должен передать Б24 
•  Условие выполнено → переход к производству.
•  Не выполнено → сделка остаётся на стадии «Предоплата»; платёж всё равно фиксируется в Timeline, чтобы не потерять историю частичных поступлений.

6.2 Проверка полноты изготовления
→  По завершении задачи «ЦМК. Изготовление изделия» отправлять REST-запрос в 1С на проверку полноты выпуска по ЗК.
Запрос: Б24 → 1С
{
  "event": "CHECK_PRODUCTION_DOC",
  "b24_deal_id": "12345",
  "client_order_guid": "22b336bd-38cc-11f1-bb30-00155d0a1150",
  "completion_date": "2026-04-22"
}
→  1С ищет все документы «Производство без заказа» по товарным позициям этого ЗК, агрегирует изготовленное количество по каждой позиции и построчно сравнивает с заказанным. Условие полноты: Σ изготовлено ≥ заказано по каждой позиции.  —  зачем: проверка только факта наличия документа (has_production_doc = true) не защищает от частичного производства — документ может уже существовать, а по факту быть готовой лишь часть изделия. Сравнение по количеству закрывает эту дыру.
Ответ: полное изготовление
{
  "status": "SUCCESS",
  "has_production_doc": true,
  "doc_numbers": ["ПБЗ-000045", "ПБЗ-000051"]
}
Ответ: частичное изготовление
{
  "status": "PARTIAL",
  "pending_items": [
    { "product_guid": "...", "ordered": 10, "produced": 6 }
  ]
}
→  SUCCESS → сделка идёт дальше, к проверке доп. комплектации (6.4).
→  PARTIAL → уведомить сотрудника ЦМК списком отстающих позиций, сделку оставить на текущей стадии; повторное завершение задачи после доизготовления запускает проверку заново.Тут надо четко прописать как 1С будет проверять в Заказе клиента что у него изготовлено а что нет 
6.3 Регламентный триггер
→  Ежедневно в 17:00 — регламентное задание 1С формирует отчёт о выработке за день. это задание мануальное 1С не формирует отчет 
→  Если есть изготовленная продукция → «Ведомость сдачи ГП на склад» → документ «Производство без заказа» → «Приходный ордер на товары». Этот же документ участвует в сверке количества из 6.2.
6.4 Дополнительная комплектация
→  При переходе сделки на стадию перед отгрузкой всегда инициировать перезаполнение ЗП, даже если состав фактически не менялся.  —  зачем: исключает риск, что ЗП тихо устареет — данные обновляются каждый раз, а не только при обнаруженном изменении.
→  Параллельно — задача сотруднику ЦМК указать доп. комплектацию. Текст задачи надо прописать 
•  Комплектующих нет на складе → «Процесс закупки комплектующих» → «Ожидание снабжения», полная блокировка до прихода товара.
•  Комплектующие есть → сделка идёт на Этап 6 «Отгрузка». Тут получается задача висит на операторе пока он ее не выполнить сделка не пойдет на стадию дальше Получается оператору придет задание и как закончит указание комплектации в 1С сам зайдет в задачу в Б24  завершит ее тут мы должны доверять полностью человеку не будем нагружать систему 
Ручное изменение сделки/ЗК сотрудником ЦМК на стадии производства обрабатывается не здесь, а в Этапе 9 «Обновление заказа» — учесть при написании Этапа 9, что триггером может быть изменение именно во время изготовления, не только после него.
